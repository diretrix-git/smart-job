01 Why This Project

This project was chosen specifically for our Python class because it demonstrates real algorithmic depth rather than a long list of shallow CRUD features. An earlier proposal was flagged by the professor as too feature-heavy with too little substance — essentially just database reads and writes with no meaningful computation.

The Smart Job Recommendation System addresses that feedback directly. At its core are two non-trivial algorithms:

  • Cosine Similarity — a vector-math-based scoring algorithm that computes how closely a user's skill set matches each job's requirements.
  • NLP Skill Extraction via spaCy PhraseMatcher — a natural language processing pipeline that reads a raw PDF resume and automatically identifies technical skills from unstructured text.

These two pieces turn the project from a basic to-do-list-style CRUD app into something that involves genuine data science, linear algebra, and NLP — exactly the kind of depth that matters in a Python course.

Request Flow

Frontend sends an HTTP request (e.g. POST /api/v1/resumes/upload) via Axios → FastAPI receives the request, validates it with Pydantic, authenticates via JWT → Service layer (NLP / recommender) does the computation → SQLAlchemy persists results to PostgreSQL → Response flows back as JSON.

04 Tech Stack & Why Each Choice Was Made

⚡ FastAPI — Web Framework

What it does: Serves our REST API endpoints (/auth, /resumes, /recommendations). Handles request routing, validation, dependency injection, and auto-generates OpenAPI docs.

Chosen over: Flask — Flask is synchronous, has no built-in validation, and requires manual OpenAPI setup. Django — Django bundles a full ORM, admin panel, and template engine we don't need; it's too heavy for a pure API project. FastAPI is async-capable, has native Pydantic validation, and auto-generates Swagger docs at /docs.

🗄️ SQLAlchemy + PostgreSQL — ORM + Database

What it does: SQLAlchemy lets us define database tables as Python classes (models) and query them with Python instead of raw SQL. PostgreSQL is the production-grade relational database storing all our data.

Chosen over: Raw SQL queries — vulnerable to SQL injection, harder to maintain. SQLite — fine for prototyping but doesn't support concurrent connections well, which matters when multiple users upload resumes at the same time. MongoDB — our data is highly relational (skills linked to users, jobs, AND courses via join tables), so a relational database is the natural fit.

🧠 spaCy PhraseMatcher — NLP Skill Extraction

What it does: Scans resume text and matches skill names from our database taxonomy. Uses attr="LOWER" for case-insensitive matching.

Chosen over: spaCy's default Named Entity Recognition (NER) — spaCy's built-in NER model is trained to recognize generic entities like people, organizations, and locations. It does not recognize technical skill names (like "Python", "Docker", "React") out of the box. Training a custom NER model would require thousands of labeled examples. Instead, PhraseMatcher against a known skill taxonomy gives us precise, guaranteed matches without any training data. Also chosen over NLTK — NLTK is older, slower, and primarily designed for academic research, not production NLP pipelines.

📐 Cosine Similarity — Matching Algorithm

What it does: Measures the angle between two binary skill vectors (one for the user, one for the job) to produce a match score from 0.0 to 1.0.

Chosen over: Jaccard Index — Jaccard only measures set overlap; cosine similarity is a more standard measure in information retrieval and is direction-aware. A trained ML classifier — would require labeled training data (user → job match/no-match) that we don't have. Cosine similarity is deterministic, explainable, and works perfectly with the structured skill data we have.

📄 PyMuPDF — PDF Parsing

What it does: Opens an uploaded PDF resume and extracts all text content into a plain string for NLP processing.

Chosen over: PyPDF2 — PyMuPDF is significantly faster and produces cleaner text extraction, especially for multi-column layouts and complex formatting. PyPDF2 frequently garbles text or misses content.

📦 Static Seeded Datasets — Data Source

What it does: Jobs, courses, and skills are loaded from curated JSON files (jobs.json, courses.json, skills.json) via a seed script into PostgreSQL.

Chosen over: Live web scraping — scraping job boards like Indeed or LinkedIn violates their Terms of Service, is fragile (breaks when HTML changes), and introduces network dependency. Static seeded data gives us a consistent, reproducible dataset for demos and testing.

🔒 JWT + bcrypt — Authentication

What it does: bcrypt hashes passwords before storing them (one-way, salt-based). python-jose generates JWT tokens so users can stay authenticated across requests without re-sending credentials.

Chosen over: Session-based auth — sessions require server-side storage and don't work cleanly with a separate frontend SPA. JWT is stateless — the token itself contains the user ID, so the backend doesn't need to look up a session store on every request.

Why Relational (Foreign Keys) Instead of JSON Arrays?

Storing skills as a JSON array (e.g. ["Python", "SQL", "Docker"]) inside the user or job row would be simpler to write, but creates serious problems:

  • No referential integrity — you could misspell "Pythn" and the database wouldn't catch it. With foreign keys, every skill reference must point to a real skill row.
  • No efficient querying — "find all users who know Python" would require scanning every row and parsing JSON. With a join table, it's a simple indexed query.
  • No shared vocabulary — the same skill can be linked to users, jobs, AND courses via the three join tables. A JSON array on each table would duplicate skill names with no shared identity.
  • No set operations — computing "missing skills" (job_skills − user_skills) is a native set difference on IDs, not a string-parsing problem.

06 Resume Parsing Flow

When a user uploads their resume PDF, here's exactly what happens step by step:

User uploads a PDF — The React frontend sends the file via POST /api/v1/resumes/upload as multipart form data. FastAPI validates it's a .pdf file.
PyMuPDF extracts raw text — parse_pdf_from_bytes() opens the PDF binary stream, iterates through every page, concatenates the text, then cleans up excessive whitespace with a regex (re.sub(r'\s+', ' ', ...)).
Skill matcher is loaded — load_skill_matcher(db) queries ALL skills from the database, creates a spaCy PhraseMatcher with attr="LOWER", and adds each skill name as a pattern keyed by its database ID.
spaCy PhraseMatcher scans the text — extract_skills_from_text() runs the cleaned text through spaCy's NLP pipeline, then runs the matcher. Each match returns a (match_id, start, end) tuple. The match IDs are resolved back to skill database IDs.
Skills are attached to the user — The user's existing skills are cleared (current_user.skills.clear()), and the newly detected skills are appended via the user_skills many-to-many join table.
Response returned — The resume record (with raw_text and uploaded_at) is committed to the database and returned as JSON. The user's skill profile is now updated and ready for job matching.

07 NLP Skill Extraction — Code Walkthrough

This is the actual, unmodified code from backend/app/services/nlp_extractor.py:

load_skill_matcher()

def load_skill_matcher(db: Session) -> PhraseMatcher:
    """
    Loads all skills from the DB into a spaCy PhraseMatcher.
    """
    matcher = PhraseMatcher(nlp.vocab, attr="LOWER")

    skills = db.query(Skill).all()

    for skill in skills:
        pattern = nlp.make_doc(skill.name)
        # Using the skill ID as the match_id string
        matcher.add(str(skill.id), [pattern])

    return matcher

How it works:

  • PhraseMatcher(nlp.vocab, attr="LOWER") — The critical piece. By passing attr="LOWER", the matcher compares the lowercased form of every token. This means "Python", "python", "PYTHON" all match the same pattern. Without this, matching would be case-sensitive and miss most real-world resume text.
  • nlp.make_doc(skill.name) — Converts each skill name string (e.g. "Machine Learning") into a spaCy Doc object that the PhraseMatcher can use as a pattern.
  • matcher.add(str(skill.id), [pattern]) — Registers each pattern with the skill's database ID as its label, so when we get a match we can directly look up which skill was found.

extract_skills_from_text()

def extract_skills_from_text(text: str, matcher: PhraseMatcher) -> List[int]:
    """
    Given a raw text and a populated PhraseMatcher,
    returns a unique list of matched skill IDs.
    """
    doc = nlp(text)
    matches = matcher(doc)

    # matches returns a list of tuples: (match_id, start, end)
    skill_ids = set()
    for match_id, start, end in matches:
        string_id = nlp.vocab.strings[match_id]
        skill_ids.add(int(string_id))

    return list(skill_ids)

How it works:

  • nlp(text) — Runs the full spaCy pipeline on the resume text, producing a Doc of tokenized words.
  • matcher(doc) — Runs the PhraseMatcher over the Doc, returning a list of (match_id, start, end) tuples for every skill phrase found.
  • nlp.vocab.strings[match_id] — spaCy stores match IDs as hashed integers internally. This line converts the hash back to the original string (which is the skill's database ID, e.g. "42").
  • set() for deduplication — If "Python" appears 5 times in a resume, we only want to record it once. Using a set automatically deduplicates.

08 Recommendation Engine — Code Walkthrough

This is the actual, unmodified code from backend/app/services/recommender.py:

cosine_similarity()

def cosine_similarity(vec_a: List[int], vec_b: List[int]) -> float:
    """Pure cosine similarity between two equal-length binary vectors."""
    if len(vec_a) != len(vec_b):
        raise ValueError("Vectors must be the same length")
    dot = sum(a * b for a, b in zip(vec_a, vec_b))
    norm_a = sum(a * a for a in vec_a) ** 0.5
    norm_b = sum(b * b for b in vec_b) ** 0.5
    if norm_a == 0 or norm_b == 0:
        return 0.0
    return dot / (norm_a * norm_b)

The Math Explained:

Cosine similarity measures the angle between two vectors. The formula is:

similarity = (A · B) / (‖A‖ × ‖B‖)
  • Dot product (A · B) — counts how many skills are shared between user and job (since vectors are binary 0/1, multiplication gives 1 only when both have the skill).
  • Norms (‖A‖, ‖B‖) — the "length" of each vector, computed as the square root of the sum of squares.
  • Result — dividing the dot product by the norms normalizes the score to the range [0.0, 1.0] regardless of how many total skills exist.

build_skill_vectors()

def build_skill_vectors(
    user_skill_ids: Set[int], job_skill_ids: Set[int]
) -> Tuple[List[int], List[int]]:
    """Builds binary presence vectors over the union of both skill ID sets."""
    all_skill_ids = sorted(user_skill_ids | job_skill_ids)
    user_vec = [1 if sid in user_skill_ids else 0 for sid in all_skill_ids]
    job_vec = [1 if sid in job_skill_ids else 0 for sid in all_skill_ids]
    return user_vec, job_vec

Example:

Python (id=1)SQL (id=2)Docker (id=3)
User skills: {1, 2}110
Job requires: {1, 3}101

The union of skill IDs is {1, 2, 3}. Each gets a 1 or 0 depending on whether the user/job has it. Cosine similarity of [1,1,0] and [1,0,1] = 0.5.

calculate_job_matches()

def calculate_job_matches(db: Session, current_user: User) -> List[dict]:
    """
    For the current user, scores every job by cosine similarity of skill
    vectors, finds missing skills, and attaches course recommendations.
    Returns results sorted by match_score descending.
    """
    user_skill_ids = {s.id for s in current_user.skills}
    jobs = db.query(Job).all()
    results = []

    for job in jobs:
        job_skill_ids = {s.id for s in job.skills}
        if not job_skill_ids:
            continue

        user_vec, job_vec = build_skill_vectors(user_skill_ids, job_skill_ids)
        score = cosine_similarity(user_vec, job_vec)

        missing_ids = compute_missing_skill_ids(user_skill_ids, job_skill_ids)
        missing_skills = (
            db.query(Skill).filter(Skill.id.in_(missing_ids)).all()
            if missing_ids
            else []
        )
        courses = recommend_courses_for_skills(missing_ids, db)

        results.append({
            "job_id": job.id,
            "job": job,
            "user_id": current_user.id,
            "match_score": round(score, 4),
            "missing_skills": [s.name for s in missing_skills],
            "recommended_courses": [
                {"title": c.title, "provider": c.provider, "url": c.url}
                for c in courses
            ],
        })

    results.sort(key=lambda r: r["match_score"], reverse=True)
    return results

The Full Algorithm:

  1. Get the current user's skill IDs as a set.
  2. Load ALL jobs from the database.
  3. For each job: build binary presence vectors over the union of user + job skills, then compute cosine similarity.
  4. Compute missing skills as a set difference: job_skill_ids - user_skill_ids.
  5. Find courses that teach at least one missing skill via course_skills join table.
  6. Sort all results by match_score descending (best matches first).

10 Known Limitations

Say these before the professor asks — it shows you understand the trade-offs.

  • Static seeded datasets — jobs and courses come from curated JSON files, not live scraping. The system can't discover new job postings on its own.
  • Binary (not weighted) skill vectors — each skill is either present (1) or absent (0). A user with 5 years of Python experience is treated the same as someone who mentioned Python once.
  • PhraseMatcher rebuilt on every call — load_skill_matcher() queries all skills and builds the matcher from scratch on every resume upload, instead of caching it.
  • Exact-phrase matching only — the PhraseMatcher looks for exact skill names. It won't match synonyms or abbreviations. "JS" won't match "JavaScript", "ML" won't match "Machine Learning".
  • No per-skill importance weighting — all skills count equally. In reality, "Python" might be more important than "Git" for a data science job, but our algorithm treats them the same.

11 Possible Improvements

  • Weighted skills by importance — assign weights (e.g. "core" vs "nice-to-have") to each skill in a job requirement, then use weighted cosine similarity instead of binary.
  • Synonym / alias table — create a mapping table where "JS" → "JavaScript", "ML" → "Machine Learning", "k8s" → "Kubernetes", and resolve aliases before matching.
  • Caching the PhraseMatcher — build the matcher once on app startup (or when skills are updated) and store it in-memory, rather than rebuilding per request.
  • Embedding-based similarity — instead of binary vectors, use NLP embeddings (e.g. sentence-transformers) to capture semantic similarity between skill descriptions, not just exact name matches.
  • Pagination on the recommendations endpoint — currently returns ALL job matches at once. For a large dataset, this should be paginated with limit and offset query parameters.

13 Likely Professor Q&A

Click each question to expand the answer:

How is the match score calculated?

We build two binary vectors — one for the user's skills and one for the job's required skills — over the union of all skill IDs between them. Then we compute cosine similarity: the dot product divided by the product of the vector magnitudes. The result is a float between 0.0 (no overlap) and 1.0 (perfect match). For example, if a user has Python and SQL, and a job requires Python and Docker, the vectors are [1,1,0] and [1,0,1], giving a score of 0.5.

Why cosine similarity instead of a trained ML model?

A trained ML model (like a classifier) requires labeled training data — we'd need thousands of examples of "user X is a good/bad match for job Y" with ground truth labels. We don't have that data. Cosine similarity is deterministic, explainable (we can show exactly which skills matched and which are missing), and works perfectly with the structured skill data we have. It's also a well-established technique in information retrieval and recommendation systems.

How does the system define a "skill"?

A skill is a row in the skills table with a unique name (e.g. "Python", "Machine Learning", "Docker") and an optional category (e.g. "Programming", "DevOps"). The skill taxonomy is seeded from skills.json. The NLP extractor uses spaCy PhraseMatcher to scan resume text for exact matches (case-insensitive) against these skill names. Skills are linked to users, jobs, and courses via three many-to-many join tables.

Is this tested?

Yes — there are 16 passing unit tests across three test files:

  • test_recommender.py (9 tests) — covers cosine similarity edge cases (identical vectors, orthogonal vectors, partial overlap, empty vectors, mismatched lengths), vector building, missing skill computation, and end-to-end job matching with sorting.
  • test_nlp.py (6 tests) — covers PhraseMatcher construction from DB, exact matching, case-insensitive matching, multi-skill detection, no-match scenarios, deduplication of repeated mentions, and multi-word skill names.
  • test_api_integration.py (1 test) — full integration test that hits the /api/v1/recommendations/jobs endpoint via FastAPI's TestClient with mocked dependencies, verifying status code, response structure, match scores, and user/job IDs.
Where do jobs and courses come from?

They come from curated static JSON files (data/jobs.json, data/courses.json, data/skills.json) that are loaded into PostgreSQL via a seed script (data/seed.py). We intentionally chose this approach over live web scraping because scraping job boards like Indeed or LinkedIn violates their ToS, is brittle (breaks when their HTML changes), and introduces network dependency. Static seeded data gives us a consistent, reproducible dataset for development, demos, and testing.

What would you improve with more time?

Five things, in priority order:

  1. Weighted skill vectors — assign importance levels to skills per job ("core" vs "nice-to-have") for more nuanced scoring.
  2. Synonym resolution — build an alias table so "JS" → "JavaScript" and "ML" → "Machine Learning" before matching.
  3. PhraseMatcher caching — build once on startup instead of rebuilding per request.
  4. Embedding-based similarity — use sentence-transformers to capture semantic relationships between skills, not just exact name matches.
  5. Pagination — the recommendations endpoint currently returns all matches at once; it should paginate for large job datasets.
Why did you use FastAPI instead of Flask or Django?

Flask is synchronous, has no built-in data validation, and requires manual OpenAPI setup. Django bundles a full admin panel, template engine, and ORM we don't need — it's too heavy for a pure REST API. FastAPI gives us async support, native Pydantic validation (type errors are caught automatically), and auto-generated Swagger docs at /docs — perfect for an API-only backend.

Why not use spaCy's built-in Named Entity Recognition?

SpaCy's default NER model (en_core_web_sm) is trained to recognize generic entity types like PERSON, ORG, GPE (locations), DATE, etc. It does not have a "SKILL" entity type. Technical skill names like "Python", "Docker", "React" would be recognized as ORG or not at all. Training a custom NER model would require thousands of manually labeled resume examples. Instead, we use PhraseMatcher with a known skill taxonomy — this gives us precise, guaranteed matches without any model training.

2. Recommendation Engine for Beginners

What is a Vector? In our system, a vector is just a list of 1s and 0s. If we have 3 total skills (Python, SQL, React), and a user knows Python and React, their vector is [1, 0, 1].

What is Cosine Similarity? It's a math formula used to figure out how similar two vectors are. Instead of just counting overlapping skills, it treats the lists of 1s and 0s as lines (vectors) on a graph and measures the angle between them. An angle of 0 degrees means they match perfectly (Score = 1.0). A 90-degree angle means they share absolutely no skills (Score = 0.0).

Code Walkthrough: recommender.py

def build_skill_vectors(user_skill_ids, job_skill_ids):
    all_skill_ids = sorted(user_skill_ids | job_skill_ids)
    user_vec = [1 if sid in user_skill_ids else 0 for sid in all_skill_ids]
    job_vec = [1 if sid in job_skill_ids else 0 for sid in all_skill_ids]
    return user_vec, job_vec
user_skill_ids | job_skill_ids
The | symbol combines the two sets of skills together (a mathematical Union). We need a master list of all skills involved in this specific matchup to create our 1s and 0s.
def cosine_similarity(vec_a, vec_b):
    dot = sum(a * b for a, b in zip(vec_a, vec_b))
    norm_a = sum(a * a for a in vec_a) ** 0.5
    norm_b = sum(b * b for b in vec_b) ** 0.5
    return dot / (norm_a * norm_b)

** 0.5
This is Python's way of doing a square root. We divide the dot product by the square root of the vectors' lengths to normalize the score to be exactly between 0.0 and 1.0.

1. Authentication (JWT & bcrypt)

What is bcrypt? We never save raw passwords in the database (like "password123"). Instead, we use `bcrypt` to "hash" them into unreadable gibberish. It's a one-way math function, meaning even if someone steals our database, they can't reverse the hash back into the password.

What is JWT? JWT stands for JSON Web Token. When a user logs in, we give them a token (like a digital VIP pass). Instead of sending their username and password every time they click a button, their browser just shows the token to the server.

Code Walkthrough: security.py

def get_password_hash(password: str) -> str:
    salt = bcrypt.gensalt()
    pwd_bytes = password.encode('utf-8')
    return bcrypt.hashpw(pwd_bytes, salt).decode('utf-8')
bcrypt.gensalt()
A "salt" is random data added to a password before hashing. It prevents hackers from using pre-computed tables (rainbow tables) to crack common passwords. We generate a salt, hash the password bytes with it, and return the safe string.

1. API Integration with Axios

What is Axios? Axios is a JavaScript library used to make HTTP requests (like GET, POST, PUT) from the browser to our FastAPI backend. We use it instead of the default browser fetch() because it automatically converts JSON data for us and provides better error handling.

What are Interceptors? In api.js, we use Axios Interceptors to attach the user's JWT token to every single request automatically. This means we don't have to manually write token logic on every page.

2. Global State Management (AuthContext)

What is the Context API? Normally in React, to share data between components, you have to pass it down manually step-by-step (called "prop drilling"). The Context API lets us create a "global bubble" of state.

How AuthContext Works: We created an AuthContext that wraps the entire app. It stores whether the user is logged in and their profile details. If the user logs out, the Context updates, and every component in the entire app instantly reacts to the change and hides protected data.
